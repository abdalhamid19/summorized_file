# 05 - استراتيجيات Rendering واختيار Framework

## الخلاصة العلمية المنظمة

أربع طرق للRendering عليها يُختار Framework. **Client** = من يفتح المتصفح. **Server** = الموقع الذي تُجلب منه البيانات.

### مقارنة طرق Rendering

| الطريقة                                 | ماذا يحدث                                                            | ميزة ذكرها المصدر                                      | عيب ذكرها المصدر                                                                                 | متى يختارها                                                         |
| --------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| [[CSR]] Client-Side Rendering           | Server يرجع HTML+CSS+JS؛ JS تشتغل في المتصفح وتجلب الداتا عنده      | لا تكلّف Server Memory ولا حملًا لأي Action على المتصفح | ليست SEO-optimized؛ جوجل وChatGPT لا يريدان render JS على Servers الخاصة بهما؛ صفحات «ملغومة» شائعة على CSR | تفاعل كثير من الزبون مع الأداة؛ لا يهمك Server. **لا** إن أردت SEO |
| [[SSR]] Server-Side Rendering           | HTML+CSS+JS تُعالَج على Server وتُرجع صفحة كاملة                    | SEO-optimized؛ ChatGPT وجوجل يحفظان نسخة ويعرضانها     | كل طلب معالجة على Server → تحتاج Serverًا قويًا                                                  | تريد SEO وتتحمل Serverًا قويًا                                       |
| [[SSG]] Static Site Generation          | صفحة HTML كاملة تُحفظ على Server وتُرجع كما هي بلا Rendering في كل طلب | وسط بين الطرفين                                        | الصفحة ثابتة؛ لا تصلح لما يتغير (منتج بمراجعات/ستوك)                                             | Landing Page وصفحات لا تتغير                                          |
| [[ISR]] Incremental static regeneration | HTML موجود مع تعديلات بسيطة عند الطلب أو عند الUpdate                 | «مسك العصاية من النص»                                  | لا تصلح في كل الأحوال                                                                            | مثال: صفحة منتج بمراجعات؛ ستوك unlimited؛ الUpdate بالمراجعة الجديدة |

> [!warning] تنبيه
> صفحة **checkout / الدفع** في E-commerce: لا CSR (زبون فاهم Development قد يعبث من Client ويبوّظ الدفع) ولا SSG. يلزم SSR.

### اختيار Framework على أساس Rendering

| Framework | طبيعة Rendering في المصدر | متى يناسب بحسب المصدر |
|---|---|---|
| [[React]] | أصله CSR (كور حقيقي يبقى CSR عند أي تحديث). فيه SSR لاحقًا. فيه معالجات للـ SEO لكن الكور يميل CSR | Application Desktop/قائم على Chrome؛ Workflow مثل n8n حيث Client يتصرف. **لا** لMarketplace/E-commerce/دليل يحتاج SEO |
| [[Next.js]] | Framework من React يقبل SSR وSSG وISR | أشهر Framework الآن؛ الثلاث طرق |
| [[Vue]] | شبه React؛ امتداد الملفات `.vue`؛ ملفات وأسماؤها مختلفة | تفاعل كثير (cards/اختيارات كثيرة)؛ Workflow أفضل من React في هذه النقطة. يعمل SSR وSSG وISR. **لا يعمل CSR خالص** — كله Server-side → يحتاج Serverًا قويًا |
| [[Svelte]] | من 2016؛ يركز على الـ Forms | إن كانت الـ Form أساسية وكثيرة في الأداة |
| [[Angular]] | «انسَها»؛ نادر من يعمل بها الآن | — |
| [[Astro]] | أساسها static؛ Dynamic بتعديل بسيط | SEO ممتاز ونتائج «حلوة جدًا» في الـ SEO |
| [[Nuxt]] | طالع من Vue؛ يعمل الثلاث طرق كما Next من React | بديل Vue الموازي لـ Next |
| Remix | طالع من React | ذُكر ضمن المكتبات |

Native React يُستخدم لمن يركز على Mobile Application. الشغال الآن أكثر: Next وAstro وأخيرًا Vue.

> [!note] كلهم واحد مع إمكانية التعديل
> الـ Default يختلف: Next أكثره Server-side لأنه نابع من React؛ Astro أصله static مع إمكانية Server-side. يمكن التعديل على الـ Default.

### Caching بعد Rendering

كل Request متكرر يحتاج [[Caching]]:
- على **CDN** لملفات HTML/JS المتكررة.
- **HTTP caching** لـ API request المتكرر على **Redis** أو نظام Caching.
بعد الـ loading: JS عند Client (React أو Server-side) تجلب الداتا بحسب Action الزبون.
