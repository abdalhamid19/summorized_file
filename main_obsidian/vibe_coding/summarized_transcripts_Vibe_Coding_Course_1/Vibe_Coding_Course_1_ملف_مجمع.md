# 01 - تعريف الكورس والمجاني والمدفوع

- يفتتح إبراهيم الشربيني (قناة سيكويشن) كورسًا عن <span style="color:#0D9488; font-weight:bold;">Vibe Coding</span>، ويترجمه: البرمجة بالذكاء الصناعي، وترجمتها الحرفية «البرمجة الحدثية».
- يذكر أنه تكلم عن الموضوع على القناة من حوالي أشهر، لكن الاسم لم يكن «Vibe Coding»؛ الاسم جديد أطلقه أحد الـ YouTubers المشاهير على مجال البرمجة بالذكاء الاصطناعي، ثم صار الاسم معروفًا على مستوى المجال كله.
- الكورس مجاني على YouTube، لكن ما سيُعمل عليه **ليس مجانيًا تمامًا**.

### ما ليس مجانيًا

| العنصر | الحكم في المصدر | التفاصيل |
|---|---|---|
| أدوات الذكاء الاصطناعي | مدفوعة 100% | Claude وChatGPT واحتمال Gemini. لا نسخة مجانية، ولا حساب طلبة، ولا رصيد مجاني، ولا DeepSeek كبديل لأدوات العمل. |

> <span style="color:#E11D48; font-weight:bold;">من يفكر «الداخل» بشيء مجاني ليصنع Business — بحسب المصدر — لا يفكر بـ Business أصلًا.</span> من يفكر بـ Business يستثمر في المدفوع اليوم كي يبدأ يجلب مالًا لاحقًا.

# 02 - الست مهارات وصورة Vibe Coder

- الهدف: ركوب Vibe Coding وتحقيق الفكرة، **لا تعلم البرمجة ولا تعليمها**. المتحدث نفسه ليس مبرمجًا ولا يعرف أن يبرمج؛ عمل أدوات وE-commerce لشركات وChrome Extension **بدون كتابة سطر واحد**، ولم يتعلم كتابة الـ Code كي يبقى محافظًا على فكر Business.
- حتى المطوّر الذي يعرف البرمجة إن نقصته هذه المهارات **لن يعرف أن يعمل Vibe Coder**.

الكورس هنا على **Web Application** لا Mobile Application.

### 1. الرؤية

لازم فكرة حاضرة كاملة: أداة أو Chrome Extension أو موقع يُحوَّل إلى Application. كثير عنده الفكرة ويقف عند تكلفة المبرمجين والتعاقد مع الشركات. في عصر الذكاء الاصطناعي الفكرة تُنفَّذ بسهولة؛ الكورس يعلّم كيف. الشرط: فكرة قوية مدروسة حاضرة في البال.

### 2. عقلية Business

الاشتغال بـ Code يُخرج من فكر Business: العقل يُستنزف في شكل الكتابة واللغة والمكتبة وعدد الملفات. المطوّر لا يتحرك إلا حين يقول صاحب المشروع «عاوز أعمل كذا». صاحب الـ Business لا يهمه كيف يُكتب الـ Code ما دامت فكرة الـ Business حاضرة؛ لغة البرمجة لا تفرّق معه.

### 3. اكتشاف الـ Bug (Bug explanation)

لا برمجة بلا مشاكل. المطوّرون يُستنزف عقلهم ووقتهم في فهم Bug وعلاقته بالمكتبة والسؤال في Stack Overflow وGitHub. Vibe Coder ينسخ Bug Copy-بيست للذكاء الاصطناعي وهو يحله. المطلوب تعلم **كيف تجد Bug وتعطيها للذكاء الاصطناعي**. بعد التحديثات (Sonnet 4.5 وChatGPT 5): مجرد Copy-بيست بلا «اعمل لي» ولا Prompt؛ وهو يعمل كل شيء.

### المهارات اليمنى (قشور تُشرح في هذا الفيديو)

1. **VS Code وGitHub:** أساسيات لأي مبرمج؛ يكفي الربط بينهما. Deployment لاحقًا من GitHub automatic للServer؛ ما طلع على GitHub حصل له Deployment والأداة اشتغلت.
2. **Docker:** عالم واسع؛ يُؤخذ الأساسي فقط. يوفّر أوامر كثيرة. Vibe Coder يأخذ ملف Docker ويضعه على Server أو Serverless فيعمل Web Application كامل بأمر واحد أو stroke واحدة. يُنسَخ الطلب للذكاء الاصطناعي: «هات ملف الـ Docker الذي يعمل Setup للحاجة الفلانية».
3. **Server administration:** وظيفة قائمة بذاتها؛ تُؤخذ القشور التي تساعد على عمل الـ Application.

الثلاث اليمنى تُغطى قشورها في هذا الفيديو؛ الثلاث الشمال في الفيديو القادم.

# 03 - المفاهيم: Frontend وBackend وHeadless

- Vibe Coding **لا يحتاج فهم لغات البرمجة ولا كيف يُكتب الـ Code**؛ الذكاء الاصطناعي يكتب الـ Code ويحل المشاكل. المطلوب: فهم **كل لغة تُستعمل في ماذا**، ومميزاتها، والمفاهيم المستخدمة وأنت تعمل الـ Application.

### أهم مفهوم: Frontend / Backend / Headless

| المصطلح | التعريف كما ورد |
|---|---|
| [[Frontend]] | واجهة ما يراه المستخدم. في هذا الكورس: نظام JavaScript. |
| [[Backend]] | دائمًا: قاعدة بيانات + API + بحث. عند المبرمجين «كله API». |
| [[Headless]] | Frontend في ناحية وBackend في ناحية، ويرتبطان عبر [[API]] أو [[GraphQL]]. |

- مدرسة WordPress (ومنها المتحدث) تظن WordPress Backend و Frontend معًا، وهو كذلك. نظام Headless — من سنة 2021 — يقول: **افصل الاثنين**. إن حصلت مشكلة في الـ Frontend تغيّره مع الحفاظ على الـ Backend، والعكس. إن كان الـ Business كله على Core واحد تُعاد برمجة كل شيء من الصفر.

### مزايا Headless كما ذكرها المصدر

1. **تغيير أحد الطرفين دون الآخر.**
2. **Security:** إن كان كل الـ Code على Application واحد يدخل الناس Chrome Console ويأخذون الـ API والبيانات. Headless يمنع ذلك بنظام Proxy ويجعل Security «100%» بحسب عبارته.
3. **السرعة:** Frontend وBackend ليسا شرطًا على Server واحد؛ يمكن نفس Server لكن كل واحد في Stack، وهذا يعطي سرعة قوية للـ Web Application.

يطلب قراءة مميزات Headless على الذكاء الاصطناعي؛ الخلاصة أنه من المفاهيم اللازمة.

### تفصيل Backend في عصر الذكاء الاصطناعي

يفصل المصدر API عن قاعدة البيانات لأن API غالبًا سيكون خاصًا بالذكاء الاصطناعي، وقاعدة البيانات لحفظ بياناته. البحث لأداة فيها بحث أو Marketplace؛ أفضل شيء ذكره اسمًا: **Typesense** (قال إنه لا يريد الدخول في الأسماء الآن، ثم سمّاه).

### Frontend المختار

- لا Ruby on Rails ولا .NET Core ولا اللغات تلك.
- لا PHP؛ لها مشاكلها مع Vibe Coding. Laravel يُذكر كBackend PHP لا يُركَّز عليه هنا.
- التركيز: **JavaScript**. أشهر الFrameworks: Next وAstro وReact وNuxt وVue وRemix وSvelte.
- للمبرمج: «ما أعرفش إلا Next / React / Vue». للVibe Coder: **كلهم واحد**؛ المهم تحقيق الهدف.

مفاهيم يجب فهم أسمائها سريعًا قبل التفصيل: Frontend، Headless، Backend، Database، API، Search، Deployment على **Serverless** أو **Server / Self-hosting container**.

# 04 - كيف تعمل صفحة الويب: Routing وAuthentication وجلب البيانات

- سيُعمل **Web Application** لا مدونة ولا أشياء WordPress.
- أي موقع إنترنت يتكوّن من: **HTML + CSS + JavaScript**. JavaScript أهم كور؛ CSS وHTML سهلة حتى لمن لم يدرس برمجة. JavaScript فيها خلافات ومشاكل كثيرة.

### لماذا ظهرت المكتبات (من 2011)

ملفات JavaScript كثيرة وتعمل لودًا كبيرًا. سنة 2011 بدأ نظام المكتبات:

| السنة | المكتبة | ملاحظة المصدر |
|---:|---|---|
| 2011 | Angular | أول مكتبة؛ تحمل JS/مكتبات جاهزة لتوفير وقت البرمجة. |
| 2013 | React | رعاها Facebook؛ خرج منها Next.js وRemix. |
| 2014 | Vue | مكتبة شبيهة بريأكت تختلف في بعض الأساليب. |
| 2016 | Svelte | من أواخر الFrameworks. |

بجانب كل مكتبة يُكتب SSR وSSG؛ يشرحها بعد قليل.

### ماذا يحدث عند طلب الصفحة

1. المستخدم يضغط رابطًا. المتصفح (Mobile أو Desktop) يرسل **request** للServer.
2. Server يعمل **[[Routing]]**: يحوّل إلى الصفحة/الملفات المطلوبة.
3. يفحص **[[Authentication]]**: هل الطالب authenticated وله access أم لا.
4. يجلب البيانات من API أو قاعدة البيانات (Backend).
5. يحدث **[[Rendering]]** — أربع طرق تُختار عليها Framework (الجزء التالي).

> [!tip] لماذا هذه الألفاظ؟
> من يعمل Vibe Coding بلا هذه المفاهيم لا يعرف ماذا يقول للذكاء الاصطناعي. لا تقل «اعمل لي صفحة write page»؛ قل **Routing**. كذلك الـ Authentication وRendering ألفاظ تُكتب في Prompt.

> [!warning] تنبيه
> أدوات مثل Lovable — بحسب المصدر — لا تعرف عمل Authentication؛ آخرها تربطك بـ Supabase وتجعل الAuthentication من خلالها. هنا لا مشكلة في العمل مع Supabase أو غيرها.


### الاستخلاص العلمي

| المفهوم | دوره عند طلب الصفحة |
|---|---|
| [[Routing]] | تحديد أي صفحة/ملف يُظهر. |
| [[Authentication]] | هل للطلب صلاحية الدخول. |
| جلب البيانات | من API أو Database أو Search. |
| [[Rendering]] | تحويل البيانات إلى صفحة تُعرض. |

# 05 - استراتيجيات Rendering واختيار Framework

أربع طرق للRendering عليها يُختار Framework. **Client** = من يفتح المتصفح. **Server** = الموقع الذي تُجلب منه البيانات.

### مقارنة طرق Rendering

| الطريقة                                 | ماذا يحدث                                                            | ميزة ذكرها المصدر                                      | عيب ذكرها المصدر                                                                                 | متى يختارها                                                         |
| --------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- |
| [[CSR]] Client-Side Rendering           | Server يرجع HTML+CSS+JS؛ JS تشتغل في المتصفح وتجلب الداتا عنده      | لا تكلّف Server Memory ولا حملًا لأي Action على المتصفح | ليست SEO-optimized؛ جوجل وChatGPT لا يريدان render JS على Servers الخاصة بهما؛ صفحات «ملغومة» شائعة على CSR | تفاعل كثير من الزبون مع الأداة؛ لا يهمك Server. **لا** إن أردت SEO |
| [[SSR]] Server-Side Rendering           | HTML+CSS+JS تُعالَج على Server وتُرجع صفحة كاملة                    | SEO-optimized؛ ChatGPT وجوجل يحفظان نسخة ويعرضانها     | كل طلب معالجة على Server → تحتاج Serverًا قويًا                                                  | تريد SEO وتتحمل Serverًا قويًا                                       |
| [[SSG]] Static Site Generation          | صفحة HTML كاملة تُحفظ على Server وتُرجع كما هي بلا Rendering في كل طلب | وسط بين الطرفين                                        | الصفحة ثابتة؛ لا تصلح لما يتغير (منتج بمراجعات/ستوك)                                             | Landing Page وصفحات لا تتغير                                          |
| [[ISR]] Incremental static regeneration | HTML موجود مع تعديلات بسيطة عند الطلب أو عند الUpdate                 | «مسك العصاية من النص»                                  | لا تصلح في كل الأحوال                                                                            | مثال: صفحة منتج بمراجعات؛ ستوك unlimited؛ الUpdate بالمراجعة الجديدة |

> [!warning] تنبيه
> صفحة **checkout / الدفع** في E-commerce: لا CSR (زبون فاهم Development قد يعبث من Client ويبوّظ الدفع) ولا SSG. يلزم SSR.

### اختيار Framework على أساس Rendering

| Framework | طبيعة Rendering في المصدر | متى يناسب بحسب المصدر |
|---|---|---|
| [[React]] | أصله CSR (كور حقيقي يبقى CSR عند أي تحديث). فيه SSR لاحقًا. فيه معالجات للـ SEO لكن الكور يميل CSR | Application Desktop/قائم على Chrome؛ Workflow مثل n8n حيث Client يتصرف. **لا** لMarketplace/E-commerce/دليل يحتاج SEO |
| [[Next.js]] | Framework من React يقبل SSR وSSG وISR | أشهر Framework الآن؛ الثلاث طرق |
| [[Vue]] | شبه React؛ امتداد الملفات `.vue`؛ ملفات وأسماؤها مختلفة | تفاعل كثير (cards/اختيارات كثيرة)؛ Workflow أفضل من React في هذه النقطة. يعمل SSR وSSG وISR. **لا يعمل CSR خالص** — كله Server-side → يحتاج Serverًا قويًا |
| [[Svelte]] | من 2016؛ يركز على الـ Forms | إن كانت الـ Form أساسية وكثيرة في الأداة |
| [[Angular]] | «انسَها»؛ نادر من يعمل بها الآن | — |
| [[Astro]] | أساسها static؛ Dynamic بتعديل بسيط | SEO ممتاز ونتائج «حلوة جدًا» في الـ SEO |
| [[Nuxt]] | طالع من Vue؛ يعمل الثلاث طرق كما Next من React | بديل Vue الموازي لـ Next |
| Remix | طالع من React | ذُكر ضمن المكتبات |

Native React يُستخدم لمن يركز على Mobile Application. الشغال الآن أكثر: Next وAstro وأخيرًا Vue.

> [!note] كلهم واحد مع إمكانية التعديل
> الـ Default يختلف: Next أكثره Server-side لأنه نابع من React؛ Astro أصله static مع إمكانية Server-side. يمكن التعديل على الـ Default.

### Caching بعد Rendering

كل Request متكرر يحتاج [[Caching]]:
- على **CDN** لملفات HTML/JS المتكررة.
- **HTTP caching** لـ API request المتكرر على **Redis** أو نظام Caching.
بعد الـ loading: JS عند Client (React أو Server-side) تجلب الداتا بحسب Action الزبون.

# 06 - Deployment: Serverless مقابل الـ Server الخاص

طريقان للDeployment بعد اختيار Rendering:

### 1. [[Serverless]] (Serverless hosting)

لا تعرف بيانات Server. ترفع Code على GitHub وGitHub يحوّل automatic إلى SSG أو SSR.

**لماذا Serverless؟** قمة Security: صاحب الحاجة نفسه بلا بيانات Server؛ من يحاول «Hacking» لا يجد بيانات لأن الأشياء ليست على Server تقليدي.

#### أ) Static (SSG) مجاني أو شبه مجاني

| المنصة | ما ذكره المصدر |
|---|---|
| Cloudflare Pages | أهمهم؛ حتى 500 زائر يوميًا مجاني؛ بعدها 5 دولار/شهر. قمة Security لموقع Static بلا Server |
| Google Firebase | Static |
| GitHub Pages | Static |
| Surge.sh | جديد «عامل شغل جامد» للمواقع الStatic؛ رفع مجاني |

موقع الشركة الثابت: المبرمج يغيّر عبر GitHub فقط.

#### ب) Dynamic ssr(بيانات من AI / بحث / API خارجي / Database)

عائلة أصلها **AWS App Runner** (أمازون؛ «الأب الروحي» وغير مشهور). البدائل المشهورة:

| المنصة | حكم المصدر |
|---|---|
| [[Railway]] | الوسط؛ الأفضل من وجهة نظره. رابط تحت الفيديو: 20 دولار إن اشتركت من الـ Link، وإلا 5 |
| Vercel | يحاول البعد عنها؛ «الفترة الأخيرة بدأت تدعم الكيان» |
| Netlify وRender | مكلفان شوية |
| Fly.io | قوي جدًا للشركات الكبيرة التي لا مشكلة لديها في المال |
| Heroku | ذُكر ضمن القائمة |

### 2. الـ Server الخاص (Self-hosting) — Maximum control

تختار Server وتعمل Deployment بنفسك: Full Control على كل شيء، ومشكلة Security عليك. في الـ Serverless لا control إلا ربط GitHub بالحساب؛ لا بيانات Server. على منصات الـ Serverless مواصفات ملفات معيّنة للـ Rendering.

**Docker أساسي** لا نقاش؛ واجهته **[[Portainer]]** (لوحة تحكم لا Terminal؛ Vibe Coding لا يتعامل مع Terminal). Kubernetes ذُكر مع Docker.

### كيف تُستخدم هذه المفاهيم مع الذكاء الاصطناعي

أمثلة Prompt ذكرها: «Deployment على Cloudflare Pages؛ ساعدني في الإعدادات» — «Dynamic على Railway» (يطلب نوع ملفات داخل الـ Code) — Vercel يطلب Extension معيّنًا في الـ Backend — Portainer على الـ Server سيُشرح بعد قليل.


### الاستخلاص العلمي

| وجه المقارنة | Serverless | Server خاص |
|---|---|---|
| بيانات Server | لا تعرفها | كاملة عندك |
| Security | قمة (لا بيانات تُسرَق من Server) | مسؤوليتك |
| التحكم | GitHub → المنصة فقط | Maximum control |
| أمثلة Static | Cloudflare Pages, Surge.sh | — |
| أمثلة Dynamic | Railway (المفضّل عنده) | Docker + Portainer على Hetzner/Vultr |

# 07 - Backend: API وقاعدة البيانات والبحث

الـ Backend غالبًا: [[API]] + قاعدة بيانات + بحث. عند المبرمجين «كله API».

### البحث

ال <span style="color:#0D9488; font-weight:bold;">Typesense</span>: القمة في البحث، مصدر مفتوح ومجاني؛ يُثبَّت على Portainer. بحث سريع قوي مناسب للذكاء الاصطناعي.

### الـ API

الـ Backend API خاص بالذكاء الاصطناعي عبر **Python** — أهم لغة تتعاون مع الذكاء الاصطناعي. مستقبلًا إن عملت موديلًا خاصًا بك بدل ChatGPT/Claude فلن يكون إلا بـ Python.

لضبط Prompt داخل Backend كل فترة: مكتبة <span style="color:#0D9488; font-weight:bold;">DSPy</span> على Python. تحسّن Prompt؛ تُثبَّت في Backend وتعطيك Prompt المضبوط لكل Request. مفتوحة المصدر ومجانية 100%. أهم مكتبتين: **FastAPI** مع **DSPy**.

### قاعدة البيانات

أعلى قيمة: <span style="color:#0D9488; font-weight:bold;">PostgreSQL</span> — مفتوحة المصدر ومجانية. أخطر عنصر Security في أي Web Application هو Database (ثم الـ API).

| مسار Deployment | المنصات / التكلفة كما وردت | ملاحظة المصدر |
|---|---|---|
| Serverless (أقصى Security) | Neon.com، [[Supabase]] (أشهرهم)، Railway، PlanetScale | Neon وRailway وSupabase تبدأ مجاني ثم مدفوع؛ المجاني لا يستمر كثيرًا. PlanetScale بلا مجاني؛ تربو سبيد؛ أقل سعر 60 دولار؛ للشركات الجاهزة |
| على الـ Host الخاص | Postgres على الـ Server مع الانتباه للـ Security | يناسب الميزانية؛ Frontend وكل شيء عندك |

تكلفة تقريبية ذكرها: من Neon/Railway تمشي بـ 5 دولار/شهر؛ Supabase أقل شيء 20 دولار «في حالة الماكس» لأقصى Security.

خطوتان على Supabase أو Neon (Railway خطوة أو خطوتين) فتصير Database جاهزة.

### إن كان الشغل ذكاءً اصطناعيًا: الذاكرة

الذكاء لا يبقى فاكر الشات وID الشات إلا بحفظ على **[[Vector Database]]**. أنواع كثيرة؛ الذي أثبت قدرته ويناسب كل الأوقات: **[[Redis]]** — Memory وVector DB في وقت واحد بعد التحديثات الجديدة.

### Analytics

إن كبرت بيانات التحليل (مثل SEO) على Database الأساسية تثقل الموقع. الحل: **ClickHouse** — يعمل Postgres أيضًا لكن مضبوط على Analytics فقط؛ مصدر مفتوح ومجاني؛ يُثبَّت على الـ Server ويوفّر load الـ Server.

> [!tip] لماذا طالت المقدمة؟
> قضى نحو نصف ساعة في المقدمة لأنها — بلاها — لا تعرف كتابة Prompt تقول فيه ماذا تريد. فهم Static وSSR وأنواع Framework والـ Serverless والـ Self-hosting كمفاهيم (لم تُرَ عمليًا بعد) يغيّر اتجاه البناء. مثال: عدم معرفة [[Headless]] يبني Frontend و Backend في واحد ويمشي سكة غلط.


### الاستخلاص العلمي

| المكوّن | الاختيار الذي سمّاه المصدر |
|---|---|
| بحث | Typesense |
| API | Python + FastAPI + DSPy |
| DB أساسية | PostgreSQL |
| ذاكرة/Vector | Redis |
| Analytics | ClickHouse |

# 08 - VS Code وCursor وربط GitHub

بعد المفاهيم: تعلم ربط [[VS Code]] و[[GitHub]]. الرؤية وعقلية Business تُؤجَّل حتى عمل الأداة.

### محررات مبنية على VS Code

VS Code برنامج مفتوح المصدر من مايكروسوفت؛ يمكن أخذ الـ Code الخاص به وبناء برنامج باسم آخر:

| البرنامج | علاقته بـ VS Code في المصدر |
|---|---|
| [[Cursor]] | قائم على كود VS Code مع مميزات الذكاء الاصطناعي؛ أشهر من VS Code حاليًا |
| Windsurf | ذُكر |
| Trae الصيني | ذُكر «الطالع أخير» |
| VS Code | العمود الفقري؛ أشهرهم في الوقت الحالي مع Cursor |

يفضّل تثبيت VS Code أولًا لا Cursor مباشرة؛ Extension VS Code يتثبّت على Cursor أيضًا.

### التثبيت قبل الربط

1. **Node.js** من جوجل (على Windows اختيار automatic؛ Mac/Linux أمر واحد من Terminal).
2. **Python:** وقت التسجيل النسخة 3.13؛ في أكتوبر 2025 الذكاء الاصطناعي آخره 3.12 و3.11 ولم يصل 3.13. يحاول أخذ نسخة أقدم قليلًا؛ دعم 3.12 حتى 2028 تقريبًا. مثال عملي: 3.11.
3. حساب GitHub (لا يحتاج شرح إنشاء الحساب).
4. برنامج **Git for Windows**.

التحقق: افتح فولدر مشروع → Terminal → New Terminal → `npm -v` (أو اسأل الذكاء الاصطناعي). اختبر بايثون بطلب Code في ملف.

### ربط GitHub

Extension **GitHub Pull Requests** أهم Extension للربط. أول مرة: يفتح رابطًا وcode تُنسخ إلى حساب GitHub. المشروع يُنشَر Private أو Public. أي تعديل في الفولدر: Commit ثم Push فيظهر على GitHub.

ملف **`.gitignore`** يُنشأ automatic ويمنع صعود `node_modules` و`.next`؛ تصعد الملفات الـ public.

### Extensions العمل

الأهم اثنان وعليهما علامة Anthropic وOpenAI: **Claude Code** (الأهم لأنه سيعمل عليه) و**Codex** الخاص بـ ChatGPT (مهم في بعض الأحوال). الفرق لاحقًا.

### عرض عملي: مشروع Next.js ثم Push

- فولدر test project → يسأل DeepSeek مثالًا (للبداية لا للعمل): `create new next.js project`.
- ينسخ الأمر للTerminal؛ اختيارات: TypeScript yes، Tailwind yes، ESLint yes، App Router / SSR yes، Turbo pack no، حسب ما قال DeepSeek.
- `cd` إلى مجلد المشروع ثم `npm run dev` → Port 3000 والمشروع يفتح.
- Push: يسأل Private/Public؛ `.gitignore` automatic.
- تعديل تجريبي: DeepSeek يعطي محتوى لـ `app/page`؛ استبدال الـ Code؛ الألوان تتبّع التعديلات؛ Commit باسم مثل «Home Page» ثم يظهر على GitHub.

> [!tip] ماذا يكفي من GitHub؟
> GitHub تفاصيل كثيرة جدًا. الذي لُقِّن هنا: **ربط GitHub بـ VS Code** — هذا وحده يمشي في Vibe Coding. الباقي يُسأل أي ذكاء اصطناعي.

### مزوّدا الـ Server الخاص

| | [[Hetzner]] | [[Vultr]] |
|---|---|---|
| السعر | أرخص بكثير | أغلى؛ تعوّض بقوة الـ Servers (تشابه قوة أمازون) |
| متى تختار | الميزانية | شغل ثقيل/موقع ثقيل يتحمل كثيرًا |
| حد أدنى ذكره | 4 CPU + 16GB بـ 25 يورو ≈ 30 دولار | لا أقل من 40 دولار؛ Dedicated CPU؛ 2 CPU + 8GB أقل شيء؛ أو 60 دولار |
| الموقع | Locations أقل؛ أمريكي، أو ألماني إن كان الموقع عربيًا (أقرب للدول العربية) | يفضّل مدينة أمريكية؛ نيويورك من الأفضل |
| نظام التشغيل | Ubuntu؛ Dedicated CPU | Ubuntu 24 (25 ليست stable بعد؛ من يسمع لاحقًا قد يختار 25) |
| تفعيل الحساب | يحتاج تفعيل أول مرة: PayPal auto-approve أو Visa ثم جواز/بطاقة. Limit أول شهر: Server واحد حتى دفع الفاتورة. Link الفيديو: 20 دولار Credit؛ من الموقع مباشرة بلا رصيد | لا تحتاج Verification. Link الفيديو: 300 دولار أول شهر؛ من دونه تسجيل مجاني بلا شيء |
| الـ Ports | باي Default **يفتح كل الـ Ports** (مريح للـ Development؛ عيب Security → تُقفَل يدويًا من Firewall) | باي Default **يقفل** الـ Ports |
| الدخول | يرسل IP على اللوحة وPassword على الـ Email؛ يطالب بتغيير Password أول دخول | IP وUsername وPassword root من اللوحة (copy-paste)؛ لا يطالب بتغيير Password (يفضّل المشي بـ Password Vultr كما هو) |
| النسخ الاحتياطي | — | يمكن إلغاء خيار Backup إن لم يُرَد |

الدخول عبر برنامج **PuTTY** (`putty download`): IP → Open → `root` → right-click للصق Password (لا Ctrl+V). على Hetzner: الصق Password القديم ثم الجديد مرتين (لا تظهر الكتابة) ثم `clear`. على Vultr: `passwd` إن أردت التغيير.

Public IPv4 مجاني على Vultr. نقطة SSH أمنية ذكرها ولم يحب تنفيذها في العرض؛ ترك Server بPassword.

# 10 - Docker وPortainer وNginx Proxy Manager

لوحة تحكم Docker: <span style="color:#0D9488; font-weight:bold;">[[Portainer]]</span> (`portainer.io`). المطوّرون يعملون Docker من Terminal؛ Vibe Coder يريد واجهة. يبدو مدفوعًا وهو **مجاني 100%**.

### تثبيت Portainer عبر الذكاء الاصطناعي

أي ذكاء اصطناعي: أوامر تثبيت Portainer على Ubuntu 24. مع التكرار يعمل الشخص documentًا خاصًا للأوامر التي مشت. الأوامر تحت الفيديو أيضًا. النمط: copy من الذكاء → right-click في PuTTY للصق. أول أمر: تحديث Server ثم تثبيت Docker ثم Portainer؛ أي سؤال `Y`.

الدخول: `https://IP:9443` (ذكر أيضًا 933 في موضع). **على Vultr فقط:** فتح الـ Ports بـ UFW لأن الـ Default مغلق (Hetzner يفتح الكل). يمكن فتح Port 9443 فقط أو تمكين الكل. أول دخول: إنشاء user وPassword (يشيل الـ checkbox) → Create user.

ارتباك الواجهة: Home → Environment → Local → Stacks. من Stacks تُثبَّت البرامج.

### مصادر الستاتكات

- `hub.docker.com` للبرامج.
- قناة/شركة **elestio** (استضافة؛ يختار «أنظف برامج»؛ Servers من Amazon وVultr وSetup automatic؛ الملفات مفتوحة المصدر): Mautic لـ Email Marketing، WordPress، Vibe Coder، Redis، Flowise لـ AI agent، Odoo المجاني، وغيرها.
- أو البرامج الـ Verified المشهورة على Docker.
- أي إيج: انسخ الDocument للذكاء الاصطناعي: «ساعدني أثبّته على Portainer» فيعطيك الخطوة بخطوة.

أول ما يُثبَّت: **[[Nginx Proxy Manager]]** (الأوامر تحت الفيديو) لأجل ربط Domain/Subdomain بالـ IP. Add stack → الصق ملف الStack من الذكاء الاصطناعي (لا يحتاج قاعدة بيانات إضافية إن لم تُرَد) → Deploy. بديل Nginx التقليدي بخطوة واحدة؛ يوفّر مشاكل Nginx الكثيرة عند المطوّرين.

دخول NPM: `http://IP:81`. الافتراضي: user `admin@example.com` وPassword `changeme` ثم تغيير الـ Email.

### مثال n8n (الهدف تعليم الربط لا تعليم n8n)

1. جهّز Subdomain على Cloudflare: A record من `n8n.vibe-code.com` (مثال) إلى IP Server.
2. في Portainer: أنشئ **Volume** اسمه مثل `n8n_data` **قبل** التثبيت.
3. n8n على Port **5678**.
4. في NPM: Add Proxy Host → IP Server (نفس Server) + Port + الSubdomain. أولًا HTTP ثم Edit → SSL → Request certificate → Agree → Save. SSL بعد ربط Cloudflare.
5. Deploy للStack في Portainer.
6. أول فتح: شاشة تنصيب (أحيانًا متصفح آخر إن لم تظهر).
7. فعّل **WebSocket** في إعدادات Proxy لـ n8n (وللأدوات التي تحتاج Data instant). بعض المواقع لا تُفعَّل فيها.

نفس النمط لـ Activepieces (قال إنها نفس فكرة n8n): Stack → Volume → Email/Password/Frontend URL → Deploy → Port 8080 → Proxy بلا HTTPS أولًا ثم Subdomain.

> [!tip] الزمن
> بTerminal/Nginx العادي: ساعتان أو ثلاث ويلزم معرفة كل خطوة. هنا: دقائق.


### خطوات النمط العام (أي تطبيق Docker)

1. خذ Document الصورة/الStack.
2. اطلب من الذكاء الاصطناعي خطوات Portainer.
3. أنشئ Volume إن لزم قبل التثبيت.
4. Deploy Stack.
5. اربط Port في Nginx Proxy Manager + Subdomain Cloudflare.
6. اطلب SSL.
7. فعّل WebSocket إن كانت Data instant.

# 11 - Railway والخلاصة وبوابة الدرس القادم

### [[Railway]] مقابل الـ Server الخاص

- Railway خدمة [[Serverless]]: لا بيانات Server عندك، بخلاف Hetzner وVultr حيث البيانات كاملة والدخول على Server ممكن أن يُستغل في «Hacking».
- Security عالية جدًا، ومعها **Limitation**: يجب المشي بطريقة معيّنة، وملفات بشكل معيّن. يُسأل الذكاء الاصطناعي أولًا: ما الملف داخل المشروع لأجل Deployment على Railway.
- Railway تفرض ملف **`railway.toml`**. مثال Prompt: «عندي مشروع بتفاصيل معيّنة؛ اعمل Deployment على Railway واعمل الملفات الخاصة بها».
- Railway تعمل أيضًا بـ Docker؛ الشرح هنا لمشاريع GitHub الخاصة.

### الحساب والربط

| المصدر | الرصيد المذكور |
|---|---|
| الـ Link تحت الفيديو | 20 دولار |
| التسجيل من الموقع مباشرة | 5 دولار فقط |

الخطوات: الحساب → Connect مع GitHub من داخل الأكونت → New → Deployment من GitHub بعد ضبط ملفات الـ toml (تفاصيلها في الفيديو القادم لأن الفيديو طال).

### القوالب بنقرة واحدة

Templates لأي شيء على Docker: n8n (مع Redis وكل شيء)، Flowise، Redis، Postgres (Database بنقرة). الشرح التفصيلي في الفيديو القادم.

### Deployment مشروع GitHub (مثال Astro)

1. GitHub repo → اختيار المشروع.
2. Deployment automatic؛ **أربع خطوات ≈ خمس دقائق** حتى يصبح Live.
3. يلزم ملفات معيّنة حتى يشتغل على Railway.
4. بعد أن يصبح أخضر: Settings → **Generate domain** (كستم Domain) أو ربط Domain الخاص.
5. اختيار Port — غالبًا **8080** بحسب ملف الـ toml.
6. أخذ الـ Link؛ المشروع يظهر (مثال: مشروع Astro).
7. المتغيرات (env) تُوضع هنا؛ شرحها في الفيديو القادم.

### طبيعة هذا الفيديو: بوابة

الفيديو مقدمة/بوابة تفتح المجال؛ وراء كل بوابة تفاصيل أكثر. فهم Portainer وRailway وFrontend/Backend يفتح مجالات كثيرة؛ الذكاء الاصطناعي يُسأل بعدها. قشور كافية من: Server أدمنستريشن، Docker، ربط VS Code بـ GitHub، وتثبيت أي Extension (سيُعمل عليه في فيديو Vibe Coding).

الجانب **الأيمن** اكتمل. ينقص الجانب **الأيسر**: Vision، Business mindset، حل مشاكل Code — في الفيديو القادم. هذا الفيديو مقدمة مهمة حتى لا يُعاد شرح Portainer وServer هناك.
