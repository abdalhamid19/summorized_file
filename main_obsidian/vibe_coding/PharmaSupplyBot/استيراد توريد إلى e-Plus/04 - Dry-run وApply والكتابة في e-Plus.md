# 04 - Dry-run وApply والكتابة في e-Plus

## الملخص

يستخدم التطبيق وضعين مختلفين:

- **Dry-run:** يبني الفاتورة ويفحصها، ثم يعرض ما كان سيُكتب. دالة الكتابة تتوقف قبل فتح اتصال SQL للكتابة في e-Plus.
- **Apply:** بعد ضغط المشغّل على Apply وتأكيده، يكتب التطبيق رأس الفاتورة وسطورها في قاعدة e-Plus داخل معاملة واحدة.

ا <span style="color:#E11D48; font-weight:bold;">نقطة أمان:</span> Dry-run لا يكتب فاتورة في e-Plus؛ أما Apply فينقل العملية إلى مسار SQL الذي ينشئ رأس الفاتورة والسطور.

## ما الذي يحدث في Dry-run؟

ينفذ `service.process_order(..., apply=False)` جلب الطلب والتحقق وبناء `PendingBill`. يستدعي بعد ذلك `erp_write.insert_pending_bill(..., apply=False)`. في كود `erp_write.py` يعرض هذا المسار محتوى الفاتورة ثم يرجع قبل جزء `INSERT`:

~~~python
if not apply:
    print("  (dry-run: NOT writing to ERP)")
    return None
~~~

هذا يمنع كتابة سجل فاتورة في e-Plus. قد يسجل التطبيق نتيجة `dry_run` في قاعدة التدقيق المحلية، وقد يحفظ ربط صنف في قاعدة المطابقات المحلية عندما تتحقق شروطه؛ هذان السجلان المحليان ليسا فاتورة e-Plus.

## ما الذي يكتبه Apply؟

يكتب `erp_write.insert_pending_bill(..., apply=True)` سجلين مترابطين:

| جدول e-Plus | المحتوى |
|---|---|
| `pur_trans_h` | رأس فاتورة الشراء: المورد، الفرع، التاريخ/الرقم، العدد والإجمالي، حالة الفاتورة |
| `pur_trans_d` | سطور الفاتورة: معرّف الصنف، الكمية، الأسعار، الخصم وبعض حقول الوحدة والمخزون |

يُنشأ `pth_id` من قاعدة e-Plus، ثم يستخدمه التطبيق في كل صف من `pur_trans_d`. وتتم عمليات الإدخال في معاملة SQL Server واحدة: عند النجاح تعمل `commit`، وعند فشل أي جزء تعمل `rollback`.

الفاتورة التي ينشئها هذا المسار معلّقة وغير مدفوعة: يضع الكود `bill_status=1` و`pth_paid=0`. الإرسال المباشر يتم إلى SQL Server باستخدام `erp.conn()`، وليس عبر API ويب عام لـe-Plus.

## تسلسل Apply في الواجهة

1. حدد الطلب من قائمة الطلبات المؤكدة.
2. افحص المعاينة والأسماء وكود e-Plus.
3. شغّل Dry-run وراجع الأسعار والإجماليات.
4. عالج أي مورد غير مربوط أو صنف ناقص أو فرق حساب.
5. اضغط **Apply selected**.
6. اقرأ نافذة التأكيد واضغط **YES, apply** للإرسال الفعلي.

الحالة `PASS` أو وجود عناصر مطابقة وحده لا ينفذ Apply؛ الكتابة لا تبدأ إلا عندما يصل الكود إلى المسار ذي `apply=True`.

## صورة البيانات المرسلة

| جزء الفاتورة | القيم المحضرة |
|---|---|
| رأس الفاتورة | المورد `ven_id`، الفرع، تاريخ/رقم الطلب، إجمالي الشراء، وعدد البنود |
| كل سطر | `itm_id`، الكمية، سعر الوحدة قبل الخصم، سعر الشراء، نسبة الخصم، سعر البيع المقروء من الصنف |
| بيانات إضافية | مرجع طلب Tawreed في الملاحظة؛ ولقطة كمية المخزون من قاعدة الكتالوج المحلية إذا توفرت |

سعر البيع الحالي من e-Plus لا يحل محل سعر الشراء القادم من Tawreed. كما أن لقطة المخزون المرسلة في بعض الحقول تُقرأ من قاعدة `catalog.db` المحلية، لا من سطر الطلب.

## منع الفاتورة الجزئية غير المقصودة

إذا كانت النتيجة `PARTIAL`، يضيف مسار الخدمة تنبيهًا ويحجب Apply افتراضيًا. يتطلب إدخال السطور المطابقة فقط تفعيل خيار `Force import PARTIAL bills`. يجب أن يكون ذلك قرارًا مقصودًا بعد مراجعة البنود غير الموجودة، لأن الفاتورة الناتجة لن تحتوي كل سطور Tawreed.

## مثال الطلب 3053985 وحدود المثال

في المعاينة السابقة ظهر `PASS` و`5/5`، والمورد `ven_id=735`. هذا يثبت أن البيانات وصلت إلى مرحلة الفحص والمطابقة. لكنه لا يثبت إنشاء فاتورة؛ لم يتم الضغط على **Apply** في ذلك المثال. لا يوجد رقم `pth_id` لذلك الطلب ضمن نتيجة المعاينة التي وثقناها.

## تنبيه أمان تشغيلي

> [!warning] لا تعرض بيانات الاتصال
> رمز الاتصال بقاعدة SQL Server يقرأ الإعدادات من الخادم. لا تضع كلمات مرور أو رموز جلسة Tawreed في ملفات الشرح أو سجل Git.
